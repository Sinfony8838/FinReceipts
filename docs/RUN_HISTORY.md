# 已保存任务：链接遗失后的只读发现

工作台增加“已保存任务”入口。关闭旧标签页、丢失任务链接后，可以从当前服务的运行库
重新找到已提交任务，打开其当前状态、证据和事件。展开列表、翻页和打开任务都不执行模型。

这与[创建响应恢复](CREATE_RECOVERY.md)解决不同阶段的问题：会话记录复用尚未确认的创建请求；
历史列表发现数据库中已经提交的任务，不恢复尚未发送的草稿，也不替用户重发创建请求。

## 接口与页面

`GET /api/runs?limit=20&cursor=...` 返回 `items` 和 `next_cursor`。`limit` 默认为 20，范围为
1 到 50；游标最长 256 字符，由服务端生成，调用方应原样传回。没有后续页面时为 `null`。
工作台每页显示 10 条，提供上一页、下一页与刷新列表。

正常条目仅含 run ID、revision、最多 160 字的问题预览、截断标志、公司、财年、状态、
已用与最大调用额度、创建及最近事件时间。不返回完整回答、财务证据、消息、租约 token 或
幂等键。列表状态可能变化，打开任务后读取当前状态；重复打开当前任务也会重新读取。

任务记录或事件校验失败时，条目只返回任务编号和 `availability=integrity_failed`，
不展示未经校验的问题或状态；工作流版本不兼容时为 `workflow_incompatible`。
正常条目为 `available`。因此列表 HTTP 200 不代表每条任务都可继续执行。

列表沿用 Host、浏览器来源检查及 API 不缓存策略。它不占模型执行名额，满载时仍可读取。
当前是本机单一信任域：能够正常访问服务的客户端可以列出该库的任务摘要；此入口没有
逐用户权限、租户隔离或公开共享能力。

## 分页与一致性

[存储实现](../src/finreceipts/runtime/store.py)没有创建新表、索引或迁移旧记录。沿现有 SQLite
内部行位置倒序读取，首次请求固定当时的最高位置，后续使用位置边界而非 OFFSET 跳页。
在现有 API 的创建和状态更新流程中，新任务不会进入这次向后翻页的结果；刷新后才可见。

每个页面在一个 SQLite 读取事务中取得候选行并校验所选任务的完整导出。游标同时绑定
首屏上界和页尾位置，以及对应任务编号的 SHA256 摘要；位置被重用但任务不同也不能继续。
对编号使用摘要还避免损坏的文本编号使游标自身变成非法格式，遮住后续正常任务。

数据库维护、删除或重排使边界对应关系失效时，接口返回 409 / `history_cursor_expired`，
页面提示刷新；格式或范围非法则为 422。游标是临时分页信息，不是身份凭据或长期书签。
[SQLite 官方说明](https://www.sqlite.org/rowidtable.html)指出，未显式声明 INTEGER PRIMARY KEY
的表在 VACUUM 后可能改变 rowid。进行维护、数据库替换或升级后应刷新列表；不承诺跨维护
操作保留原分页顺序。用户可保存的稳定入口仍是 run ID URL。

跨页只固定创建范围，不固定每条任务的状态快照；后台推进或取消后，后续页面可看到新状态。
页面回到第一页时复用已读取的首屏，点击刷新重新建立范围。读取错误保留已经打开的任务，
不会清空当前结果或创建替代任务。

最多 50 条是返回条目数和选中任务数的上限，不是整页耗时或内存的绝对上限：每个选中任务
仍要读取并校验自己的 checkpoint 和事件链。当前没有全库搜索、总数统计或生产容量指标。

## 验证与复现

基线 `b582f11` 的 `GET /api/runs` 返回 405，工作台没有从运行库发现旧任务的入口。
本轮新增[24 项测试](../tests/test_run_history.py)，覆盖：

- 空库、参数边界、页大小、只校验选中页面、不返回全文数据；
- 翻页期间新增任务、取消任务、并发提交与单页快照一致性；
- 正文、事件、行身份及文本编号损坏时，其他任务和后续页面仍可读取；
- 游标边界位置被重用后拒绝继续，重新打开库且数据库结构不变；
- 执行名额满载时仍能列出任务，Host 与来源拒绝仍生效。

补充审查还复现了第一版游标被损坏任务编号阻断的问题：下一页错误返回 422。改为绑定
编号摘要后，该负例通过。失败输出保留于本地 `runs/run-history-20261018/cursor-damage-before.txt`。

[真实 Edge 演练](../scripts/browser_history_smoke.cjs)在新库创建 12 个任务，以 10 + 2 翻页；
中途插入新任务，原范围仍为 12 个唯一 ID，返回首屏不漂移，刷新后才看到新任务。
关闭原标签页后，从无任务片段的新页面找到原任务；12 份完整导出保持相同，调用额度未增加。
还验证了恶意 HTML 形式的问题只作为文字显示、列表网络错误不清空当前任务、打开当前任务
重新读取取消状态、单条坏记录隔离，以及桌面和 390 px 手机宽度无横向溢出。

完整工作台流程、上一轮的创建丢响应及服务重启恢复也重新通过。最终 Python 全仓为
**871 passed / 1 skipped，61.22 秒**；跳过仍为 Windows 符号链接权限。
本轮未调用真实模型、运行远程 CI 或执行 Docker 重建。

python -m pytest tests/test_run_history.py -q

最终浏览器记录在本地 `runs/run-history-20261018/browser-final-v3/`，创建恢复回归在同级
`create-recovery-final-v2/`。演练只修改新建的测试数据库；其中故意保留一条损坏记录作为负例，
不能将整个演练库当作业务数据使用。源码与结果通过该轮 `evidence.json` 的摘要关联。

最终产物复核发现旧浏览器脚本把响应解析后再用 `JSON.stringify` 保存，导致例如 `0.0` 变成
`0`，破坏现有 Python 编码规则下的摘要。原数据库通过完整性校验，重存文件失败，诊断记录
保留于 `export-roundtrip-diagnosis.json`。浏览器脚本现改为保存原始 HTTP 响应字节，并立即
用 Python 校验实际文件；上述两组最终回归的导出均通过该检查。UI 通过不再代替导出文件验收。
