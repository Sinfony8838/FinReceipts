# SQLite 备份与恢复演练

企业里的备份问题不止是“文件复制成功”：需要确认在线写入没有被漏掉，恢复后的预算、
幂等键与证据链仍一致，以及一次失败的恢复不会覆盖正在使用的数据。
本项目提供离线管理命令，演练使用独立数据库和 FakeLLM，不接触已有运行记录。

## 一致性与发布边界

`runtime-backup` 用 SQLite Online Backup API 从只读连接复制数据库。在复制前开启读事务，
固定一个快照；WAL 模式下其他连接仍可提交，快照不会把不同提交的 checkpoint 和事件拼在一起。
长时间读取会延迟 WAL 回收，需要为源盘和备份盘留足空间。不能直接复制正在使用的主数据库，
也不能分别复制主文件、WAL、SHM 并假定它们来自同一个提交点。

产物是一个**此前不存在的目录**：

```text
backup-001/
  runs.sqlite3       # 独立数据库，不依赖 WAL / SHM / journal
  manifest.json      # 复制、校验及文件同步完成后才发布
```

校验按以下顺序进行：

1. 当前运行库的严格 schema 白名单，拒绝未知表、触发器、视图和索引。
2. SQLite `integrity_check`，以及没有归属任务的孤立事件检查。
3. 逐任务验证行主键、workflow 版本、事件序号、hash 链、checkpoint、请求与事实摘要。
4. 保存数据库 SHA256、字节数、任务/事件数，以及各任务的末尾事件 hash、revision、预算、状态和原实现摘要。

`runtime-verify-backup` 重新检查这些字段。`runtime-restore` 先验证备份，复制到新目录，
再检查**实际恢复出的字节**与内容，最后发布 manifest。现有目录（包括空目录）、文件、目录别名
均由目录独占创建拒绝，命令没有覆盖选项。备份文件是可信管理员持有的离线产物，校验期间不可修改。

失败、磁盘满或进程退出可能留下数据库或 `manifest.pending`；缺少有效 `manifest.json`
的目录不构成可用备份。失败目录保留供检查，重试必须使用新目录，工具不会递归清理。
不要将应用直接指向失败目录里的数据库。文件同步和同目录 manifest 重命名已实现，
未验证断电、磁盘控制器故障或文件系统目录项持久性，不宣称断电容灾保证。

实现依据：[SQLite Online Backup API](https://sqlite.org/backup.html)、
[Python sqlite3 backup](https://docs.python.org/3.12/library/sqlite3.html#sqlite3.Connection.backup)。

## 操作步骤

使用当前已安装环境运行，显式传入实际运行库路径。以下路径只是例子；父目录须已存在，
输出目录须不存在。所有命令成功退出码为 0，失败为 2，成功时输出 JSON manifest。

```powershell
finreceipts runtime-backup --database D:\runtime\runs.sqlite3 --out D:\backups\backup-001
finreceipts runtime-verify-backup --backup D:\backups\backup-001
finreceipts runtime-restore --backup D:\backups\backup-001 --out D:\recovery\restore-001
```

`--copy-timeout 30` 控制备份复制阶段，在分页进度/SQLite 重试边界检查超时。
它不是整个命令的硬截止时间，文件 I/O、完整性扫描和 hash 校验仍取决于数据量及存储速度。
工具不创建不存在的源库，不迁移 schema，不调用模型，不清空租约，不重置预算。

正式切换须由管理员另行完成：停止旧实例和 worker；对新目录验证、抽查导出与对照复核；
确认原运行记录的 `implementation_id` 与准备运行的代码兼容，再把应用运行库配置指向恢复路径。
保留旧库和备份以便回退。工具不自动改配置、不停止服务、不切换流量。
不要同时运行旧库和恢复库承接同一组任务，否则预算与幂等约束会成为两个互不协调的分支。

恢复后的状态保持原样：

| 快照状态 | 恢复后行为 |
| --- | --- |
| 已保存回答、等待核验 | 可从核验节点继续；不需要重新获取事实或调用模型 |
| 正在执行且有预留预算 | 保留租约及预算；未到期不允许 resume，到期后需显式 resume |
| 已取消、已完成、预算耗尽 | 保留终态；恢复本身不会重新执行 |
| 原实现摘要与当前代码不同 | 保留历史内容；已有运行时版本检查仍阻止不兼容续跑 |

原运行中请求在外部提供商处是否完成，备份无法判断。显式恢复可能重复未提交调用，
预算预留保留也不等于跨系统 exactly-once。恢复库首次开始服务后会发生正常写入，原 restore
manifest 成为恢复时的历史凭据；之后应创建新备份，不能继续用旧 manifest 验证已变化的活动库。

## 可复现演练

```powershell
.venv\Scripts\python.exe scripts\backup_restore_drill.py --out runs\restore-drill-new
.venv\Scripts\python.exe -m pytest tests\test_backup.py -q
```

演练在同一个源库创建三个场景：已回答待核验、预算已预留的运行中任务、已取消任务。
它保留原始导出与恢复导出，验证逐字节结构一致、源库逻辑记录未变，并在恢复库完成核验，
证明恢复库的模型调用次数为 0。另有主文件复制漏记录、恢复目录已存在及损坏备份负例。

测试额外覆盖：真实 WAL 未 checkpoint 的提交、固定快照期间另一个线程提交、schema/事件链
损坏但 SQLite 结构检查通过、恢复过程磁盘满、复制后字节篡改、复制超时，以及发布 manifest
前真实子进程异常退出。命令行回归通过子进程执行备份、验证、恢复及重复恢复拒绝。

本轮本地证据保存在 `runs/backup-restore-20261018/`，Git 忽略该目录；失败记录保留，
以 `evidence.json` 指向的最终记录为准。首次验证发现 Windows 的只读文件句柄不能 `fsync`，
修正为对自产物使用可写句柄。WAL 负例夹具也改为真实持有读取快照，避免最后一个连接关闭后
checkpoint 使负例失去前提。不是把一次成功复制等同于恢复验收。

2026-10-18 本机最终全量回归为 **745 passed / 1 skipped**，新增备份恢复测试 31 项；
跳过项仍为 Windows 符号链接权限。Ruff 检查及格式检查通过。独立演练保留 **3 个任务、
9 条事件**，恢复前后导出一致、恢复库模型调用为 **0**；主文件复制负例只读到 **0 个任务**。
首轮全量回归的测试漏导入失败也保留，不将其视为通过。

## 能力边界与技术讲述

可以现场解释的问题是：“为什么备份文件能打开，仍然不能认为恢复成功？”
展示主文件复制漏掉任务的负例，再展示在线快照、语义校验及恢复后继续核验，最后验证预算
和取消状态不变。每个结论都有输入、负例和可检查输出，不虚构生产事故或业务收益。

当前只覆盖 SQLite 中的 durable runs 和 events。配置、凭证、HTTP 缓存、PIT 原始文件、
评测产物、外部模型状态和独立证据归档不在备份范围内。manifest 的 hash 能检测意外变化，
不是签名，无法防止管理员同时改写数据库和 manifest；源库中合法但错误的数据仍会被备份。
运行时业务可用性还取决于原依赖、provider 配置和兼容代码，schema 通过不等于所有历史任务可续跑。

尚未实现自动轮换、异地存储、加密、保留策略和版本迁移。小型离线夹具上的耗时仅用于定位
本轮操作，不代表生产 RTO/RPO。没有做真实业务库演练、断电测试或远程 CI 验证。
