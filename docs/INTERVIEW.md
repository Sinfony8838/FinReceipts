## 可直接使用的项目描述

**FinReceipts｜可追溯金融研究 Agent 与证据核验工作流**

**项目背景：** 面向财务问答中数字、指标、期间与主体容易错配的问题，构建以确定性财务证据
核验驱动作答修订和模型升级的 Agent Harness，提供证据收据、可恢复执行与浏览器演示。

**技术栈：** Python、LangGraph、FastAPI、Pydantic、SQLite、SSE、SEC XBRL、pytest、GitHub Actions。

**简历条目（按岗位选择其中三项）：**

- **证据驱动的 Agent 控制流：** 组织作答—核验—修订—模型升级流程，将提取的数值声明与
  XBRL 事实及派生计算对应，保留各次回答和核验记录；区分错误标记反馈与检索数值反馈，
  避免把证据辅助修正误称为模型自我纠错。
- **固定证据的可恢复执行：** 为研究任务冻结事实集、请求及实现摘要，通过 SQLite 事务
  原子提交步骤状态和事件；使用幂等创建、版本比较、worker lease 与 token 校验，拒绝旧版本推进
  和失效 worker 的结果提交。补齐创建响应丢失后的页面恢复，重启服务并刷新后仍找回原任务。
  已提交步骤可恢复，未知外部调用结果需显式处理。
- **外部调用与资源控制：** 在模型和工具调用前预留预算；模型返回后遇到写库争用仍保留未知占用。
  限制输入大小、上传与响应等待，保留超时或断连后未退出线程的名额；使用真实 HTTP 验证过载拒绝与恢复。
- **故障诊断与恢复验证：** 实现安全错误码和请求关联、在线 SQLite 备份与非覆盖恢复；
  通过写锁、进程退出、磁盘错误和 WAL 负例验证事件与预算一致性，并用真实 Edge 验收工作台流程。
- **异常输入与交付验证：** 处理长空白回溯、批量审计开销和数值溢出；超限整次拒绝，区分
  无法重试的输出失败与可恢复中断。补充 sdist/wheel 隔离安装门禁，检查安装后的 API、CLI 和静态资源。

不要加上未经验证的“生产级”“零幻觉”“节省 98%”“分布式高并发”等表述。
如需附验证规模，引用[按提交划分的验证索引](VERIFICATION_INDEX.md)：`2101f7d` 的本机离线回归
为 **939 passed / 1 skipped**，独立安装包和安装后的 Edge 最近验收到 `19be01f`，运行实现摘要一致。
测试数量不代替业务收益或模型
效果；Docker 重建和远程 CI 仍没有当前通过证据，不把不同轮次的数字相加。

## 90 秒项目介绍

我做的是一个金融研究 Agent，用财报事实检查模型回答，再驱动修订并交付证据。
同一回答可以同时做数字匹配和年度语句核验，展示金额正确但公司、指标或财年错配的情况。

工程上我重点处理外部调用与本地状态之间的失败边界。例如模型已经返回，数据库却被锁住，
这时不能简单重跑节点。我在调度前预留预算，用事务提交状态和事件，并通过版本与 worker token
拒绝迟到结果。页面断开后同步线程也可能继续运行，所以并发名额要等线程退出才归还。

这些设计都有可运行的负例：真实写锁、进程异常退出、关闭 TCP 连接，以及主库复制漏掉 WAL
记录后的恢复对照。现场可以查看任务状态、实际调用和预算，而不只看一条成功回答。

项目另有 30 题的真实模型反馈策略对照。我把它与故障测试分开解释：前者讨论特定样本上的质量
和调用开销，后者验证运行行为。当前仍是本机工具，多租户和实际容器重建没有验收结论。

## 常见追问与回答要点

### 1. 为什么没有六个或更多 Agent？

这个任务中，财务数值匹配可以用明确规则完成。让多个模型重复发表意见会增加调用和失败路径，
但并不自动增加证据。我先把角色收敛为可观测的节点；是否增加研究、写作或审阅 Agent，
取决于是否存在明确的独立上下文、工具集合和可衡量收益。

### 2. 你的创新具体是什么？

不是发明 checkpoint、SSE 或引用核验，而是把它们与金融证据绑定成可复现的工作流：
恢复不换事实集，预算不因失败重置，同一份证据可以重新审计不同的语义条件。
现场可以用错指标案例展示“金额匹配通过，但语句核验不通过”。

### 3. 为什么另写 runner，没有直接使用 LangGraph SqliteSaver？

本轮需要把业务检查点、面向客户端的事件和预算预留放到明确的事务边界里。
runner 只执行已有四类节点，共享节点函数和路由，且有与 LangGraph 的结果一致性测试。
我没有把它叫作官方 checkpointer。更复杂的并行图、子图或分布式调度应采用成熟运行时，
再通过事务 outbox 解决事件一致性；当前选择的代价是只支持这个小型图。

### 4. 你实现了 exactly-once 吗？

没有。数据库状态和事件可以原子提交，但模型提供商不参与这个事务。
如果模型已经执行而本地尚未提交，恢复可能重复调用。我的处理是提前预留预算、保留未知占用、
要求显式恢复，并用 token 防止旧结果写回。真正避免重复外部副作用还需要提供商幂等键或可查询的请求状态。

### 5. 两个请求同时推进会怎样？

它们必须携带读到的 expected_revision。第一个在 SQLite 写事务里领取 lease 并增加版本，
第二个拿着旧版本会得到 409。lease 到期后可以显式恢复，但旧 token 即使拿到了结果也不能提交。
这验证的是本地共享数据库的并发隔离，不是跨地域分布式调度能力。

### 6. 取消真的能停止收费吗？

取消会阻止之后的预算预留和结果提交，不能撤回已经送到模型服务器的请求。
因此 UI 说明这个边界。调度次数也不是精确账单：SDK 可能内部重试，中断调用的 token 用量可能无法获取。

### 7. SHA-256 能证明证据是真的吗？

只能证明字节是否与指定摘要一致。事件哈希链可以检测修改和截断，外部保存的最终 anchor
可以帮助发现整链重写，但没有签名、可信时间戳和独立来源证明时，不能保证真实性或历史可用性。
固定 FactLookup 也不等于完整 SEC 原始响应快照。

### 8. 为什么数字正确还会显示未支持？

数字匹配不理解所有语境。年度语句绑定只接受定义好的主体、指标、财年、单位和表达范围。
错指标可能被判为矛盾，未知语法则会弃权。即使一段正确的自然语言超出了语法范围也会未支持，
所以不能把“未支持”等同“错误”，也不能把“支持”扩大成整篇正确。

### 9. SSE 与普通进度条有什么区别？

原问答接口的 SSE 是当次节点流；新接口将事件存进数据库并分配连续序号，客户端带
Last-Event-ID 补读。读事件没有执行副作用，刷新也不会重跑模型。这一版是有限补读流，
还没有常驻连接 heartbeat 或 token streaming；前端在推进后继续补读即可。

### 10. 如何证明恢复不是重新跑了一遍？

测试先完成 answer，再重建 RunStore 和服务对象，把模型与数据 provider 替换成“一调用就失败”
的函数。继续 verify 能成功，且模型计数仍为 1。还有子进程在预算预留后直接退出的测试，
重启后能看到占用仍存在，不能靠恢复获得额外额度。

### 11. 你测的六个案例是准确率吗？

不是。它们是手写诊断输入，专门覆盖正常年度语句、错指标、错公司、错年份、裸数字和无数字。
测试目标是验证两种核验条件的预期差异，不代表真实用户问题分布或模型泛化。
要测真实效果，需要独立数据、明确的错误分母、模型版本、成本记录和多条件对比。

### 12. 怎么迁移到生产？

先明确身份、租户和数据边界，在现有请求体与响应等待限制之外补足部署层连接限制、
外部工作硬截止策略及真实部署验收，再按实际并发需求评估
队列、数据库扩展、lease 心跳、审计保留与指标。迁移时保留现有幂等、状态版本、证据绑定和
预算预留契约，做故障和负载测试。现有 SQLite 已持久化，不能把“换数据库”直接当作可靠性提升。
不要为了简历先引入 Kubernetes，却没有真实部署与运维证据。

### 13. 页面关闭和取消任务是一回事吗？

不是。页面断开只代表客户端不再等待；已经运行的同步线程可能继续，durable run 仍可能提交。
显式取消会撤销 lease，拒绝迟到结果，但仍不能撤回外部模型请求。两种情况下都不能提前归还
仍被线程占用的执行名额。可以用[断连案例](ENGINEERING_CASES.md)展示名额保留和后续恢复。
HTTP 等待超时也遵循这一约定：504 不代表模型未调用，SSE 的 HTTP 200 仍可能以错误事件结束。
已保存任务先查询状态和 revision；实现与实测见[请求限制](REQUEST_LIMITS.md)。

### 14. 为什么备份还要验证业务内容？

主数据库文件能打开，不代表包含 WAL 中的最新提交。在线备份后，我除了检查 SQLite 结构，
还检查事件链、请求和事实摘要，并在恢复库继续核验已经保存的回答。恢复原样保留预算与租约，
不自动重放模型。容器命名卷配置已经补齐，但本机 Docker 引擎不可用，所以容器重建仍没有实跑结论。

### 15. Host 和来源检查能当登录吗？

不能。它们限制浏览器跨源请求，原生客户端能伪造请求头；本机知道 run ID 的程序仍能读任务。
多人使用必须另做身份认证和逐任务授权。当前证据只支持本机浏览器边界检查，不支持租户隔离。

### 16. 后端实现幂等键就能防止重复创建吗？

还要保证客户端重试使用原键和原输入。我用浏览器让创建请求真实提交后丢弃响应，发现刷新
页面会丢失内存中的键，重试产生第二个任务。现在发送前先保存会话记录，刷新后确认原请求，
成功后先写入任务 URL 再清理记录。重启服务的浏览器演练验证只有一个任务、导出不变；
存储不可用时不发送创建请求。这个结论只覆盖同一标签页，不冒称跨设备或模型调用恰好一次。
对于已经提交但链接遗失的任务，工作台另有[只读分页列表](RUN_HISTORY.md)。它校验所选任务，
隔离坏记录，并用插入范围与位置身份避免新任务挤动向后翻页；这与重发创建请求是不同操作。

### 17. 超时配置为什么还不够？

超时结束 HTTP 等待，不保证同步计算已停止。一个约 1 KB 的空白输入就曾使数字提取超过
3 秒未完成；允许范围内的 256 句审计也曾超过 8 秒。先修正重复回溯和前文扫描，再给
字符数与数值数设明确上限，超限整次拒绝。256 句本机测量降至约 0.135 秒，但不能据此
声称生产 SLA。零值证据还暴露了相对误差的无穷值问题：诊断不可用应返回 null，不能把核验
矛盾变成 500，或写成误差为零。实现和负例见[计算边界](REQUEST_LIMITS.md#数值分析的计算边界)。

### 18. 所有失败都可以重试吗？

供应商暂时不可用和已提交答案违反核验边界是两种情况。后者从同一节点恢复只会重读同一份
异常答案，所以我只对白名单内的数值超限/溢出设终止失败，保留证据、答案和已用预算；
其他异常仍按既有中断规则处理。真实浏览器验证失败任务不能反复恢复，但缩小问题后可以
另建任务，原记录不变。这不是根据异常字符串猜测所有错误是否永久。

### 19. 安装门禁比源码目录里的测试多证明了什么？

editable 安装可能掩盖缺失资源或源码路径依赖。我从 sdist 构建 wheel，在新环境安装带哈希的
锁定依赖，用隔离解释器确认实际导入位置，再调用安装后的 API/CLI、访问静态资源并重启检查
原始导出。故意删去 runs.js 的 wheel 必须被拒绝。这个结果不证明构建后端锁定、无网络安装、
所有最低依赖版本或字节级可重复构建；最近通过的包属于哪个提交也必须说明。

## 五分钟现场演示

1. 离线启动，打开 `/workbench`，说明 fake 模型只是固定回答演示。
2. 创建 Apple FY2023 任务，指出 evidence digest、run ID 与调度上限。
3. 推进一步，刷新页面：仍在 verify，模型调度次数仍为 1。
4. 点击“继续执行”，展示错误回答被核验驱动修订，以及中文时间线和可展开的原始事件。
5. 点击“复核当前回答”，比较“数字匹配”和“语句核验”两列，说明年度语法弃权与金额匹配的不同含义。
6. 运行 `scripts/runtime_demo.py` 的错指标案例，展示更明确的语义冲突。
7. 导出 JSON，用校验脚本和另存的 anchor 核对；最后说明目前不具备的生产能力。

## 界面改进怎么讲

“最初页面偏向工程演示，口号和技术 JSON 抢占首屏，完成标记也容易让人误解为答案完全正确。
我先保留原始截图，再把设置和结果分区，将高级选项折叠，把数字匹配与语句核验并列展示。
中文摘要便于阅读，原始事件和证据仍可以展开或导出。

实现时我没有为了展示引入新框架，而是抽取共享 CSS 和主题脚本，并保持后端协议不变。
我用真实离线接口验收创建、修订、刷新、导出和问答，异常 UI 用明确标注的测试夹具覆盖。
检查五种宽度和原生 200% 缩放时，还发现并修复了任务地址改变却显示旧结果的问题。
最终有 64 组布局检查和 42 项相关后端回归记录，而不是只凭截图判断完成。”
