# FinReceipts 工程故障案例

FinReceipts 用财务事实核验模型回答，并保留修订过程。运行层需要解决的实际问题是：
外部调用已发生时怎样恢复、用户断开连接后怎样控制资源，以及恢复出的数据能否继续使用。
以下四个案例把触发条件、处理方式、代价和复现入口放在一起，便于审查或现场演示。

## 模型已返回但数据库暂时不能写

模型调用和 SQLite 提交不在同一个事务里。若模型已经返回，而数据库被其他连接锁住，
直接重试整个节点可能重复调用；把任务改回 ready 并退还预算，也会丢失已发生调用的记录。

运行层在调度前持久化预算预留，再通过 revision 和 lease token 限制结果提交。
检测到 SQLite 写争用时，保留 running 状态与预留预算，向客户端返回 503 和等待提示。
客户端先查询当前状态；租约到期后，只有显式确认可能重复调用才能恢复。
磁盘满、I/O 和损坏错误不会被当作普通写争用无限重试。

负例让 FakeLLM 在返回前启动另一个真实 SQLite 写事务。结果是调用发生 1 次、预算占用 1 次，
回答尚未提交；租约到期后恢复，原预算只有 1 次的任务进入预算耗尽，模型不再被调用。
这证明了未知调用占用被保留，没有证明供应商执行恰好一次。

```powershell
python -m pytest tests/test_store_resilience.py::test_lock_after_model_response_preserves_budget_until_explicit_recovery -q
```

实现：[事务与租约](../src/finreceipts/runtime/store.py)、
[调用前预留](../src/finreceipts/runtime/service.py)。更多故障见[可靠性记录](RELIABILITY.md)。

## 页面断开但同步模型线程仍在执行

取消 HTTP 等待不能可靠终止已经开始的同步模型调用。若在请求结束时立即释放信号量，
旧线程仍在运行，新请求又拿到名额，实际并发就会超出配置上限。

准入控制同时记录请求是否结束和它拥有的工作线程是否退出，两者都满足才归还名额。
满额时立即拒绝新的昂贵操作，不额外排队；读取任务、导出、取消和恢复不占用该执行名额。
明确取消任务会撤销结果提交资格；单纯关闭页面不会自动取消 durable run。

2026-10-18，工程案例整理轮在 `d50ce9e` 的 Python 实现上，用延迟 250 ms 的 FakeLLM 发起 32 个回环 HTTP 请求：

| 配置容量 | 成功进入执行 | 503 拒绝 | 实测模型并发峰值 |
| --- | ---: | ---: | ---: |
| 1 | 1 | 31 | 1 |
| 4 | 4 | 28 | 4 |

另一案例在模型被受控阻塞时关闭真实 TCP 连接，名额仍占用 1，新请求得到 503；
工作线程退出后服务恢复。该实验验证容量约束，没有测量生产吞吐或真实提供商延迟。

```powershell
python -m pytest tests/test_admission.py::test_cancelled_http_task_cannot_free_a_still_running_model_slot -q
python scripts/admission_load.py --out runs/review-admission-001 --capacity 1 4 --requests 32 --delay-ms 250
```

实现：[准入与工作线程计数](../src/finreceipts/app/admission.py)。当前限额是单进程的，
没有跨 worker 协调、公平队列或租户配额；这是需要保留的设计代价。详见[准入记录](ADMISSION_CONTROL.md)。

后续[请求限制](REQUEST_LIMITS.md)把同一约定延伸到响应等待超时：真实 HTTP 返回 504 或
SSE 错误时，阻塞模型仍占名额，新执行得到 503；已保存任务的预算不会退还。
还验证了实际字节超限与慢上传在调用模型前被拒绝。

## 备份文件能打开但没有最新任务

WAL 模式下，已提交记录可能尚未写回主数据库文件。只复制主文件得到的副本可以正常打开，
却漏掉这些记录；仅做文件存在检查或 SQLite 结构检查不足以证明恢复成功。

备份使用 SQLite Online Backup API 固定读取快照，检查数据库结构、事件归属、hash 链、
checkpoint、请求和事实摘要，再发布包含 SHA256 的 manifest。恢复只创建新目录，
再次验证复制后的实际字节，不覆盖原库，不重置预算，也不自动启动模型调用。

本轮重新演练了 3 个任务、9 条事件。主文件复制负例读到 0 个任务；在线备份恢复出的导出
与原记录一致，继续核验时恢复库调用模型 0 次，运行中任务显式恢复后仍保留 1 次预算占用。
固定快照会延迟 WAL 回收，因此长备份仍需关注存储空间。此演练不证明生产恢复时间或断电容灾。

```powershell
python -m pytest tests/test_backup.py::test_wal_commit_is_backed_up_even_when_raw_file_copy_misses_it -q
python scripts/backup_restore_drill.py --out runs/review-restore-001
```

实现：[备份与恢复](../src/finreceipts/runtime/backup.py)。操作与兼容性边界见[恢复说明](BACKUP_RESTORE.md)。

## 创建已经提交，但页面没有收到任务编号

后端有幂等键仍不够：如果前端只把键存在内存，提交成功后的响应丢失，再刷新页面重试，
就会换新键创建第二个任务。真实 Edge 负例在服务端返回 201 后丢弃响应，复现了两个不同 run ID。

工作台现在在发送前保存原键和完整输入；恢复时锁定输入、显式确认同一请求。成功后先保存
run ID 地址，再清除记录和补读事件，避免后续网络错误丢失任务入口。存储不可用时不发请求，
记录损坏或放弃找回需要用户明确处理。

验收在丢弃响应后还重启了隔离服务：刷新确认只得到原任务，SQLite 中任务数为 1，
完整导出不变，模型调度次数为 0。该机制只覆盖同源同一标签页的会话恢复，不保证跨设备找回。

```powershell
node --test tests/test_create_journal.cjs
node scripts/browser_create_recovery.cjs runs/review-create-recovery-001
```

实现、浏览器验收和存储边界见[创建恢复说明](CREATE_RECOVERY.md)。

## 现场演示顺序

在已经安装依赖的仓库环境中运行上述命令；输出目录必须尚不存在，不复用历史实验目录。

1. 先在[工作台](RUNTIME.md)展示创建、推进和刷新后保留的回答与预算，交代 FakeLLM 的作用。
2. 选择一个最相关的故障案例，先解释预期不变量，再执行对应的负例测试。
3. 展示演练生成的 JSON：核对实际计数、任务状态和恢复前后导出，而不是只展示 PASS 字样。
4. 说明一个当前代价，例如未知调用可能重复、单进程准入、长快照占用 WAL。

案例整理轮的原有三个故障测试共展开为 5 项用例，当时实跑为 **5 passed**。
备份与容量脚本也在该整理轮的 Python 实现摘要下重跑通过。整理轮没有重新调用真实模型。
