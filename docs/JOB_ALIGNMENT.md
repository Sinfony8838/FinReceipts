## 参考设计及采用的取舍

| 来源 | 本轮实际参考 | 在 FinReceipts 中的应用 / 取舍 |
|---|---|---|
| [LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence) | checkpoint 与跨运行 store 的职责；内存 saver 无法跨进程 | 明确持久化边界；本轮实现应用级节点 runner，共享已有节点，不冒充官方 saver |
| [Deep Agents](https://github.com/langchain-ai/deepagents) | 把工具、上下文、状态与可观测性视为 harness 的组成部分 | 把财务证据和预算放进 harness；不引入无需使用的 shell 或文件写入工具 |
| [Microsoft Agent Framework](https://github.com/microsoft/agent-framework) | 显式工作流和 Agent 编排作为独立工程层 | 保留可检查的状态推进，而不是多加几个角色 prompt |
| [Claude Code 公开权限文档](https://code.claude.com/docs/en/permissions) | 工具动作在执行前按规则决策 | 在固定的财务工具参数范围内执行；模型不能扩展公司、期间或工具类型 |
| 用户提供的 `D:\Claude code源码\claude-code-2.1.88` | 只读查看权限模块与 sessionRestore 的少量片段，注意恢复不仅是聊天记录，还涉及成本和上下文状态 | 预算先写、恢复保留状态；未复制其中实现，也未把其视为本项目可再分发的开源依赖 |

## 与参考简历如何形成差异

对方简历中的技术实现和数值没有在本轮独立验证，因此不判断其真实优劣。
以其表述为比较输入，FinReceipts 应展示更容易复现和解释的垂直问题：

| 参考简历强调的能力 | 本项目可展示的对应能力 | 适合深入讨论的差异 |
|---|---|---|
| 多 Agent 状态机 | 作答、核验、修订、升级模型的共享状态路由 | 为什么确定性 verifier 适合控制受支持数值，而不是让 Critic 只给主观分 |
| SSE 进度事件 | 持久化事件 ID、游标补读、状态与事件原子提交 | 断线不会触发重跑，重复推进有版本冲突；有限补读流的边界 |
| PostgreSQL checkpoint | SQLite 本地节点检查点、并发 fencing、显式恢复 | 检查点与外部副作用不是一个事务；无法承诺模型请求 exactly-once |
| 信源可信度评分 | 固定事实集、原始来源字段、证据摘要、两种核验条件对照 | “引用存在”“金额能匹配”“语义归属受支持”是三个不同问题 |
| 模型路由节省费用 | 既有升级路由 + 本轮持久化调度 / 工具预算 | 能证明预算不因恢复重置；没有新账单证据就不写节省百分比 |
| 代码沙箱 | 本轮只有范围明确的只读财务工具 | 不把工具白名单说成操作系统沙箱或真实模型抗注入能力 |

优先把当前主线做成可现场演示的完整故事。向生产后端岗位扩展时，下一组独立目标应是
认证及租户隔离、任务队列 / PostgreSQL、审计保留、观测指标和真实负载测试。
向 RAG 岗位扩展时，则需要文档解析、混合召回与独立检索评测，当前不应在简历冒领。
